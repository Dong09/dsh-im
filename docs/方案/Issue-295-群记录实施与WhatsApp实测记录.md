# Issue #295：群记录实施与 WhatsApp、飞书、QQ、Telegram 实测记录

日期：2026-10-18。实施基线：dsh-im 5.0.3（`d9df48bd`）。

关联[方案](./Issue-295-六渠道群消息与群文件共享存储方案.md)与 [Issue #295](https://github.com/xmanrui/dsh-im/issues/295)。

## 实现结果

- 一个插件公共 SQLite 保存群、消息及附件元数据，原始文件存放于公共 `group-files/`，不使用机器人、会话或工作区作为所有权维度。QQ 因跨应用标识未经验证，暂按应用来源隔离，不承诺跨应用共享。
- WhatsApp、飞书、Telegram、Discord、Slack、QQ 的实际入站群事件在回复过滤前默认自动归档。收到第一条普通群消息及附件就开始保存，无需先 @ 机器人或逐群开启。
- 全局设置新增「通用」Tab，默认滚动保留 14 天，正整数可调。启动、每小时及修改期限后清理；查询与文件读取即时排除过期内容。群文件原件随消息过期，会话副本沿用既有入站附件规则。
- 文件下载使用两路并发、60 秒超时及 100 MiB 内部上限，还受平台更低的限制；保留下载状态，重启中断不标为成功。不持久化 Token 或资源下载 URL。
- 新增 `dsh_im_group_history` 和 `dsh_im_group_file`。当前群由宿主实际请求绑定；拒绝模型指定其他群，以及无群来源、已结束、混入 Web 输入或不同群的回合。消息查询分页、限条数及响应体积，文件按需生成会话副本。
- Slack 增加普通公开/私有频道消息订阅与归一化。飞书可单独增量授权群消息采集，保留“仅 @ 回复”，不会因采集授权改为回复所有消息。

数据默认位置为 `~/.dsh/integrations/dsh-im/`，支持既有 `dshHome` / `DSH_HOME` 配置。界面入口为 **DSH 设置 → IM机器人 → 齿轮「通用设置」→ 通用**。

后续补充：飞书扫码新增与“补全权限”（包括 `/repair`）统一加入 `im:message.group_msg`，保留已有 `im:message:readonly`。同步更新中英文授权提示及成功后的权限状态，保留原回复模式。回归覆盖权限清单、新增默认模式、两种已有回复模式、权限状态重新加载，以及状态写入失败不能报告本地激活成功；本次未执行飞书真实扫码授权。

该补充的 `npm run check` 通过：构建成功，4,234 项测试全部通过，包产物校验通过。

随后按用户确认的默认采集要求，移除通用设置中的群列表、刷新按钮、逐群开关及对应 RPC。旧库中原有的关闭标记不再阻止采集，已有群身份和记录保留。新增自动测试验证新群首条未 @ 消息及文件自动保存、旧库升级兼容；此次调整未重新进行 WhatsApp 真实消息验收。

## 初版 WhatsApp「test」群实测

以下为初版的实际操作记录，当时存在逐群开关；当前版本已改为默认自动采集，不再需要第 1 步中的刷新和开启操作。

使用已连接的 WhatsApp 关联设备账号和真实桌面客户端完成，未向其他群或联系人发送测试内容。模型请求通过回复已有机器人消息触发，遵循现有寻址规则；本次没有把原生客户端的 @ 操作列为实测通过项。

1. 正常群内交互后发现 `test`，在通用设置刷新列表，确认默认 14 天并开启采集。
2. 发送不含 @、不引用机器人消息的普通文本，包含 `GH295_TEXT_MARKER=TEXT_BLUE_6294`。
3. 发送普通文件 `gh295.txt`，共 96 字节，文件正文含 `GH295_FILE_MARKER=FILE_ORANGE_7481`。
4. 核对普通文本与文件均已保存，文件状态为 `ready`，本地原件与发送内容一致。发送前后会话映射与机器人发出消息 ID 集合均未变化，确认静默采集没有触发模型或回复。
5. 回复机器人消息，要求先查询群记录及文件列表，再获取文件副本并实际读取正文；请求不提供两个标记的答案，明确不允许直接查数据库或其他目录绕过工具。
6. 最终回合依次成功调用群消息查询、群文件列表、文件副本工具及宿主 `read`，读到上述两个标记。宿主回合正常结束，WhatsApp 群中实际收到含两个正确标记的回复。

实测期间修复了两处集成问题并重试至成功：

- 宿主的运行时/时间上下文快照也使用 `user/message` 事件，最初被当成混入的外部请求，导致当前群工具拒绝访问。现在只忽略已知宿主来源的快照/通知，真实 Web/CLI 或其他群输入仍会拒绝共享授权，并有回归测试。
- 附件列表的空错误字段最初为 `undefined`，被宿主拒绝为不能无损序列化的 JSON。现在输出 `null`，消息、附件及文件副本输出均加入 JSON 往返一致性检查。

初版实测结束时保留测试群采集开启及默认 14 天，未修改其他渠道的平台权限。

4. 两次普通消息入站前后，机器人会话映射和已处理交互消息集合均未变化，确认保存过程没有创建模型会话或触发回复。
5. 原生 @ 机器人，要求查询指定标记的消息、查询文件列表、获取文件副本并实际读取正文。请求只提供查找标记和文件名，不提供答案，且禁止直接扫描数据库或其他目录。

7. 再次重启加载修复后，在群内新发起 @ 请求。依次成功执行两次 `dsh_im_group_history`、一次 `dsh_im_group_file` 和宿主 `read`，正确返回两组代号及数量，回合正常结束；飞书群话题中实际收到正确回复。读取的是重启前已保存的消息和文件，验证了持久化。

本次飞书的未 @ 普通文字保存、未 @ 文本附件保存、按群查询和附件正文读取均通过。实测也覆盖了新话题会话读取先前保存的群记录，不依赖原保存时的会话。

随后按用户要求重新进行一轮实测：未 @ 发送 `GH295_FS_RETEST_TEXT`（项目「蓝鲸-8532」，预算 280 元）和中文文件名 `群文件测试.txt`（仓库 A-719，库存 46 件，120 字节）。均自动保存且未触发模型交互，文件原件逐字节一致。再以不含答案、也不指定工具名的自然语言 @ 查询，机器人自动完成群消息查询、文件列表、文件副本及正文读取，正确返回四个值，飞书群内收到结果。本轮未修改功能代码。
